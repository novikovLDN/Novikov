# ADR-0007. Заказ сервера — конечный автомат, провижининг за адаптером

**Статус:** принято, 8 сентября 2026.

## Контекст
Сейчас заказа серверов нет вовсе: кнопки на `/vds` ведут на
`/subscribe` (подписка VPN) и `/contact`. Есть ли у партнёра API для
выдачи — открытый вопрос (`QUESTIONS.md` №7).

## Решение
Статусы заказа, как в ТЗ (9.4):

```
draft → pending_payment → paid → provisioning → active
                    ↓        ↓         ↓
                cancelled  failed  suspended
```

Переходы описаны в одном месте и покрыты юнит-тестами. Каждый статус
имеет свою страницу и своё письмо.

Провижининг — за интерфейсом `ServerProvisioner`. Две реализации:

- `api` — когда у партнёра есть API;
- `manual` — заявка падает в очередь, оператор выдаёт руками, статус
  двигает через админку. Человек при этом видит честную страницу
  ожидания со сроком, а не «сервер готовится» без конца.

## Последствия
- Продажу серверов можно запускать **до** появления API у партнёра.
- Срок выдачи на витрине пишется тот, который реально держит
  выбранная реализация. «≈60 секунд» без `api` писать нельзя.
- Очередь: BullMQ + Redis, если Redis появится; до тех пор — таблица
  задач в PostgreSQL. Второй инфраструктурный сервис ради трёх
  заданий в день не заводим.
