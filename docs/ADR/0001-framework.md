# ADR-0001. Остаёмся на Next.js App Router

**Статус:** принято, 8 сентября 2026.

## Контекст
ТЗ (7.1) предлагает Next.js либо Astro с островами, если анализ
покажет преимущество по производительности маркетинговых страниц.
В проекте Next.js 16.2.1 (последняя 16.3.4), App Router, RSC,
`output: standalone`, 58 API-маршрутов, вход, оплата, интеграции.

## Варианты

**А. Next.js, как сейчас.** Витрина статическая, продуктовые потоки
серверные. Ничего не переносим.

**Б. Astro для витрины + Next для продукта.** Витрина отдаёт меньше
JS, но появляются два приложения, два деплоя, два набора токенов,
общий заголовок и футер в двух местах, а переход между витриной и
кабинетом становится полной перезагрузкой.

**В. Полный переезд на Astro.** Пришлось бы переписать вход, оплату,
вебхуки и синхронизацию с панелью. Риск уронить работающую кассу
ради оформления.

## Решение
Вариант **А**.

Замер на текущей сборке: критический путь `/vds` — 10 JS-чанков,
168 КБ, из которых 70 КБ занимает сам фреймворк. Astro убрал бы
примерно эти 70 КБ. Наши собственные 98 КБ он не убирает — их
убирает дисциплина импортов, и это дешевле, чем второе приложение.

Замер, подтверждающий, что дело в дисциплине, а не во фреймворке:
курсор в корневой разметке импортировался из модуля, который на
уровне файла тянет gsap с плагинами, — библиотека уезжала в общий
чанк и грузилась на каждой странице, включая кабинет.

## Последствия
- Обновляемся до 16.3.4 и React 19.2.8.
- Бюджет JS (≤ 180 КБ gz) держим правилами импорта и проверкой в CI,
  а не сменой фреймворка.
- Витрина остаётся статической: числа приходят из модулей на сборке.
